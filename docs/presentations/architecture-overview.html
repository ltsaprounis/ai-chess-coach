The product in one loop

Fetch a player's games. Analyze them.
Then let a model explain what the engine found.

Syncchess.com archivePublic API, no auth. Games cached locally, openings classified on the way in.
→
AnalyzeStockfish, every positionCentipawn loss per move, judged against fixed thresholds, aggregated by game phase.
→
CoachLLM, on requestA deterministic report becomes a prompt; the model narrates it and can call the engine to check a line.
  • The engine does the judging; the model does the explaining. No figure in a prompt is computed by a language model — every number is aggregated in Python from stored evaluations first.
  • The model can reach the engine, not the filesystem. A single analyze_position(fen) tool is published to the coach; every built-in shell, file and web tool is disabled on every path.
  • Nothing expensive happens twice. Games, analyses, advice, explanations and profiles are all cached in SQLite, and an LLM call only ever fires on an explicit user action.

The rule that shapes everything

Components cannot see each other — and CI proves it

Decoupling that lives in a style guide erodes. Here it is two import-linter contracts that fail the build: an independence contract over the six leaf components, and a three-layer contract putting api above them and domain below.

Only api composes

The engine never calls storage; the coach never opens the database. The API layer holds every wire between them, so a component can be read, tested and replaced on its own.

Config is injected, never imported

One component reads the YAML file and the environment. Everything else receives depth, thresholds, worker counts and file paths as plain arguments — so nothing else needs to know a config system exists.

Shared rules live in domain

Phase boundaries are a good example: engine and coach both derive them, cannot import each other, and read the same constants — with a test asserting the two implementations agree.

  • The seam is a function, not a dependency. The coach's engine tool is an injected FEN → candidate lines callable that the API layer builds from the pool. Same trick for the chat toolkit.
  • The frontend shares no code with the backend at all. It compiles against types generated from the OpenAPI schema; hand-writing a response type is a review blocker. SSE payloads are the single documented exemption.

Idempotent by construction re-runnable

The write is an upsert, so a repeat sync refreshes rather than duplicates — which is what makes a full re-fetch a safe way to backfill a column added after the games were stored.

Classification rides ingestion

Opening lookup is a cheap in-memory hash of positions, so it happens at ingest instead of becoming a second pass. Unmatched games simply stay unclassified.

Ingestion stores nothing

It fetches and parses into domain objects and yields them a month at a time. It does not know a database exists — the API layer writes.

Openings book: 3,808 ECO lines from the pinned lichess-org/chess-openings submodule · classification reads the first 30 plies · retries back off on 429/502/503.

Judgecp loss per moveEval delta from the mover's side, judged against injected thresholds.
→
Persistone analysis rowStamped with the analysis version; aggregates pre-derived so stats never re-parse it.

In parallel, the browser holds an SSE stream: a snapshot on connect, then per-position progress and per-game completion, ending in run_done. Losing the stream does not stop the run — the UI says so and offers to re-attach.

Reproducible on purpose

Every search starts a fresh game token, so carried transposition state cannot make an evaluation depend on search history. An eval is a pure function of position, depth and binary — worth ~4% of speed, and the reason re-analysis agrees with itself.

Versioned, so re-analysis is free to trigger

Bumping the analysis version — or raising the configured depth — marks every stored row stale through the ordinary "needs analysis" query. No migration, no new endpoint.

Degrades, doesn't refuse

A missing Stockfish binary is not fatal at startup: analysis and live eval answer 503 with a build hint, while sync, stats, reports and coaching keep working.

Defaults: depth 16 · 2 workers · 100 newest games per run · one run per player at a time · thresholds 50 / 100 / 200 cp for inaccuracy / mistake / blunder.

  • The prompt is a product surface, not an implementation detail. The UI shows the exact text that was sent, so template changes are snapshot-tested and carry a version.
  • Both the prompt and the advice are cached together — keyed on player, agent, prompt version, window and time control, so two coaches never share a row and a reworded template never serves stale advice.
  • Coverage is stated, never implied. When analysis covers less than the requested scope, the prompt says so and names which figures the shortfall touches — and the UI flags advice whose coverage has since been overtaken.

The deterministic layer

The model narrates. It never computes.

build_report is pure Python aggregation over stored analyses — the largest component in the backend, and almost none of it is LLM plumbing. Everything the coach says traces back to a number produced here, because a model will narrate whatever it is handed without complaint.

Volume — every stored game in scope

  • Win/loss record, colour split, opposition strength
  • Ratings and their dated peaks per time control
  • Monthly game counts, streaks, how games actually ended
  • Opening repertoire counts

Quality — the analyzed subset only

  • Loss per move, overall and by game phase
  • Judgment counts, error patterns, turning points
  • Per-opening loss columns and blunder rates

Two lists, two denominators

Computing everything over the analyzed subset made a partly-analyzed archive report a "current rating" from whichever game the engine happened to reach last. Ratings and records need no engine, so they may not be restricted to it.

Move-weighted, never a mean of means

Every loss figure is total loss ÷ total moves. Averaging per-game averages makes a 15-move loss weigh as much as a 90-move grind — and drags every endgame figure toward zero for players who rarely reach one.

Absent is not zero

A phase never reached reports None, not 0.0 — which would be indistinguishable from flawless play. Every phase carries its own move count so a thin sample is visible rather than inferred.

Prompt flows

Four LLM surfaces, one component

Coaching brief

In: the whole report over a window.
Out: one markdown brief, written to the student, naming a single biggest lever rather than a flat list.
Cached on player + agent + prompt version + scope.

Player profile

In: compact facts projected from the report, over a time control's full history.
Out: a few sentences about the student, written in the third person for another coach to read.
Stored per player per time control.

Move explanation

In: one ply's context, live candidate lines, and the stored profile block.
Out: streamed prose on why the move cost what it cost.
Cached on game + ply + agent.

Chat

In: a scope seed (one game, or the whole report) plus four read-only tools.
Out: a streamed reply, persisted before the terminal event.
Transcript is the source of truth.

  • The profile is the reuse payoff. Who-is-this-student used to be re-derived by every feature that spoke to them. Now it is computed once and embedded as one ~250-token block at the top of the other prompts — one place to improve it.
  • Cached output becomes conversation history, not context. Opening a chat after reading an explanation prepends that explanation as the first assistant turn, so the thread continues from what the student just read.
  • A fifth surface deliberately uses no model at all. Dashboard highlights — blunders and brilliancies — are static analysis over stored evaluations, kept out of the report so the prompt doesn't grow thousands of rows.

Anatomy of a prompt

Data first, instructions last — always in that order

Profile block (optional) Who the student is, in ~250 tokens. Facts one line each, then the stored narrative — block-quoted, so a heading inside it cannot forge a section boundary in the host prompt.
Scope The student, the window requested versus the span actually covered, and coverage as "N of M games" — with an explicit caveat when analysis falls short.
Data sections Recent form, phase table with denominators, monthly trend, milestones, how games end, the repertoire split by colour, error patterns, turning points with their FENs. Rendered by shared functions, so the brief, the profile prompt and the chat seed cannot drift apart.
Instruction block The only place that says what to produce — which is why one persona can serve several artifacts.

Rules the data cannot enforce

Register: the brief is written to the student in the second person, while the data describes them in the third. Attribution: an opening is only the student's if it appears under "systems the student chose" — never advise dropping a line they merely face. Honesty: say when the data does not support a conclusion instead of filling the section anyway.

One scale, one name

Every loss figure is in pawns, and no template says "ACPL" anywhere. The acronym once expanded to one scale and redefined the figure as another: the same opening read 5.16 in the brief and 516 in the dashboard. Conversion now happens only where a string is produced, and a test asserts the data half of every template is clean.

Persona

One coach, three artifacts — and one genuine exception

A single provider carries a single system prompt that serves the brief, the profile narrative and move explanations alike. So the persona names none of them: it establishes the coach, states that the figures it is handed are already computed, and defers what to write to the instruction block each template ends with.

Why not one persona each?

A persona saying "write the coaching brief" misdirects the other two. A move explanation is not a brief and re-averages nothing; the narrative is a briefing about the student, for another coach — which such a persona would flatly contradict.

Chat gets its own

Its instructions arrive once in the seed rather than in a block at the end, and every turn after the first is a conversation rather than a request for a finished piece. That is a real difference, so it gets a real second persona.

Register is per document

A first-draft narrative opened "You are a rapid player" — telling the reading coach they were the rapid player. Person is now stated outright in each instruction block rather than left for the data's headings to imply.

Chat's rule is stated versus recalled, not context versus tools: facts in the seed are established and may be quoted, but any claim past them — another game, another result — must come from a tool result in that conversation. Scoped any wider, the rule would ban the briefing the model was just given.

Keeping the model honest

Grounded, bounded, and unable to write a URL

Grounded engine tool

The engine reaches the model as an in-process MCP tool — analyze_position(fen), FEN in, candidate lines out. The brief's instructions require running it on the turning points it cites and stating the actual refutation, not just naming a better move. Rendered positions carry their FEN precisely because the tool takes one.

Bounded budgets

Eight agentic turns each for the brief, an explanation and a chat message — three separate constants, tuned independently. The profile narrative runs one turn with no tools at all: it summarizes aggregates and asserts no concrete lines, so there is nothing to verify. Built-in shell, file and web tools are disabled everywhere.

Fenced citations

Game ids are UUID-plus-username strings; one mistyped character is a broken link. So the model is offered short handles — [g1], [g2] — and a post-processing pass mints the URLs from the report itself.

  • Every failure mode degrades soft. A model that ignores the citation rule yields a plain-text reference; an invented handle renders as its own text; model-authored link definitions are stripped, so a handle cannot be redefined from inside the advice.
  • A spent budget is a message, not an error. The turn after the cap returns "finish your answer with what you have gathered so far" as a tool result. The model wraps up in its own words instead of the run dying mid-sentence.

Scope is structural, not asked for

The toolkit is built per message, already bound to one player. The model passes filters; it cannot pass a username. get_game refuses another player's game even when handed its id directly.

Two windows, on purpose

get_opening_stats takes no parameters and always uses the thread's own window. find_games lets the model choose its own — because that is how a student asks: about one opponent, or one month.

What is not there

No write tools. No raw SQL tool, now or later. No built-in shell, file or web tools — disabled on every provider path. And the profile narrative gets no tools at all: one turn, nothing to verify.

Coach Your London itself is fine — 0.38 pawns a move through the opening is not what is costing you these games. The pattern is what happens once Black hits back in the centre. In your game against marko77, 21.Qh5 allowed Nxe5, and the engine has Black three pawns up straight after it. That is a middlegame habit, not an opening choice.

What just happened

  • The seed was quotable; everything else was not. The repertoire figure could have come from the briefing — the specific game, its moves and its refutation had to come from tool results in this conversation.
  • Four calls, out of a budget of eight. Each one is a turn; the model chose the sequence, not the app.
  • The link id came from find_games. Chat has no link-minting pass, so a game reference is only legitimate if a tool returned its id — never recalled from memory.
  • Pawns throughout, idea before number. The tool results name the unit themselves, because they land mid-conversation with no header above them.
  • Then it is persisted. The pair of messages and the provider's new resume token are written before the terminal event reaches the browser.

No API keys

Both shipped providers ride a local CLI login — a Claude Code session or a GitHub Copilot seat. Authentication and billing sit with the user's existing subscription; the app holds no secret. Keyed providers are the reason the seam exists, not a prerequisite for using it.

Unbuilt means unconfigurable

The provider type lists implemented providers only, so naming a planned one fails at config load rather than mid-request. An exhaustiveness check in the factory makes the type-checker complain if the two ever drift apart.

Resume is an optimization

A provider may resume a warm session it named; it must be able to replay the stored transcript instead. A resume that fails before any output falls back silently — one that fails mid-stream surfaces as an error, because a silent restart would contradict what the student already saw.

Several coaches can be configured at once and picked in the UI. Models are pinned explicitly, not tracked through a floating alias — cached advice is keyed by agent id, so a model changing behind a stable id would let two models share one cache row.

The cost model

Engine time is free. Model calls are not.

That one sentence governs the whole backlog. Analysis can be generous — run it over the archive, re-run it when the method changes. Every LLM call, by contrast, is bounded by explicit user intent and written down so it never happens twice.

Two version constants, two jobs

The prompt version is a cache key. Rewording the brief invalidates old advice rather than serving it against a template that no longer exists.

The profile version is row metadata. It flags a stored narrative as stale in the UI and must never silently re-bill — the narrative is expensive and meant to be durable.

  • Window keys would strand the durable artifact. A "last 30 days" boundary moves every midnight, so keying the narrative on it would mint a fresh key overnight and orphan every stored row. Time control is stable — and a 2100 bullet player and their 1500 rapid self really are different students.
  • The gaps are written down, not papered over. Analysis staleness keys on depth and version but not on the configurable thresholds; the explanation cache carries no prompt version. Both are recorded as findings with designs attached — regeneration stays the user's explicit choice.

Constraints and non-goals

What this system deliberately is not

Accepted constraints

  • Single-user and loopback-only. No auth, no ownership boundary, no rate limiting, no spend ceiling — named as prerequisites for a network deployment rather than built speculatively.
  • One process, in-memory run state. A restart loses in-flight run tracking; finished analyses are already durable.
  • chess.com only, standard chess only. Variants and custom start positions are dropped with a warning.
  • GPL-3.0-or-later. python-chess is copyleft and imported directly, so the assembled backend already was a combined work; the licence states what was true rather than leaving a permissive label on it.

Considered, then declined

  • A normalized, game-neutral database. Priced at about a week, mostly in storage and its tests; perspective ids cost one string and buy the same thing while tracked players rarely meet.
  • A job queue or worker process. Background asyncio tasks in the API process, cancelled cleanly on shutdown, are enough at this scale.
  • An ORM. Stdlib sqlite3, hand-written SQL, numbered migrations.
  • Streaming the coaching brief. It returns one JSON blob; only explanations and chat stream.

Known and scheduled rather than hidden: migrations are not failure-atomic, the opening phase is still a flat 20-ply cutoff pending book-exit refinement, and single-PV stored analyses cannot tell whether a safe alternative existed — so a few merely-strong sacrifices are awarded as brilliant. Each is an entry on the backlog with a design, not a surprise.

How it was built

Docs first, then one agent per component

The first five commits are documentation — the proposal and a build plan per component — and the sixth is the first line of code. That order is the method, not an accident: an agent that starts cold needs a written contract to work against, not a codebase to infer one from.

One sub-agent per component

Eight component agents, each pinned to its own doc, scope and boundary rules. Independent single-component tasks run in parallel — they touch disjoint directories by construction. Work that spans components stays in the main session, where the contract change is decided and documented first.

A ninth agent that only reads

A read-only boundary reviewer checks a diff against the guidelines and the component docs — imports, typing, error discipline, docs drift. It reports; fixes go back to the owning component. No agent grades its own work.

Docs have three levels of authority

A live backlog, designs written up but not built, and an archive that is history — never citable as current behaviour, never a plan to resurrect. That rule is what keeps a fast-moving project's own history from becoming a source of false claims.

  • One local command is the CI gate. make check runs the same ruff, pyright, import-linter and pytest chain the pipeline runs, so a green local run means a green pipeline.
  • CI touches no network, no real model, and no engine. Recorded fixtures and stubs only; the real-engine test is opt-in and skips when the submodule is absent. A domain or interface change must update its component doc in the same commit.
